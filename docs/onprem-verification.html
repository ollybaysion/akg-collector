⚠ 로컬에서 fixture 로만 검증됨 — 이 체크리스트는 사내망에서 진행

akg-collector 사내 반입 검증 체크리스트

Phase 0~4 는 전부 구현·머지됐고 테스트 74개는 fixture 로 통과한다. 그런데 실 Oracle 스키마·실 akg 인스턴스로는 한 번도 돌려본 적이 없다 — 이 문서는 사내망에서 그 첫 실행을 안전하게 단계별로 밟는 순서다.

github.com/ollybaysion/akg-collector · 사용법 전체는 docs/usage.html

시작 전에

  • 사내망에서 레포를 내려받고 npm install — oracledb 는 6.x thin 모드라 Oracle Instant Client 설치가 따로 필요 없다(로컬에서 가짜 주소로 접속 시도까지는 확인됨).
  • Oracle 읽기 전용 계정 — ALL_TAB_COLUMNS / ALL_COL_COMMENTS / ALL_TAB_COMMENTS / ALL_CONSTRAINTS / ALL_CONS_COLUMNS / ALL_INDEXES / ALL_IND_COLUMNS / ALL_TABLES 조회 권한. 대상 스키마가 접속 계정과 다르면 SELECT_CATALOG_ROLE 같은 추가 권한이 필요할 수 있다 — 이 SQL 자체가 사내에서 처음 검증되는 것이라 이 지점에서 막힐 가능성이 가장 크다.
  • 사내 LLM 게이트웨이 URL(+필요하면 키) — OpenAI 호환 Chat Completions 만 있으면 된다.
  • akg 서버에 editor 역할 토큰 발급 — akg-user.mjs add <id> editor.
  • 테스트용으로 희생시켜도 되는, 중요하지 않은 작은 테이블 하나를 미리 골라둔다 (5단계에서 씀).

단계별 검증

1
discover — 접속·권한이 되는지부터
가장 싸고 가장 먼저 걸리는 검증. Oracle 접속 정보와 권한만 있으면 된다.
export ORACLE_USER=... ORACLE_PASSWORD=... ORACLE_CONNECT_STRING=host:1521/service
npx akg-collector discover --owner <스키마>
  • 테이블 목록이 나온다 (빈 목록이면 owner 철자·권한부터 의심)
  • 목록에 미리 골라둔 테이블이 보인다

실패하면: ORA-00942 류라면 ALL_TABLES 조회 권한 문제. 빈 목록이면 owner 대소문자(Oracle 은 기본 대문자)나 스키마 이름 자체를 의심.

2
describe — SQL 매핑을 사람이 직접 대조
이 세션에서 짠 5개 카탈로그 쿼리(컬럼·PK·FK·인덱스·통계)가 실 스키마에서 맞게 도는지 확인하는 핵심 단계 — 로컬 테스트는 "SQL 이 이런 행을 돌려준다고 가정"했을 뿐, SQL 자체는 여기서 처음 탄다. 
npx akg-collector describe --owner <스키마> --table <테이블>
  • 컬럼 타입 표기 — VARCHAR2(20) 처럼 길이가 문자 기준(byte 아님)으로 맞는지
  • NUMBER(18,6) 처럼 precision·scale 이 실제 정의와 같은지
  • primaryKey 배열 순서가 실제 PK 컬럼 순서와 같은지 (복합키일 때 특히)
  • foreignKeys 의 refTable·refColumn 이 맞는지 (복합 FK 가 있으면 최우선 확인 대상)
  • indexes 목록에 PK/UNIQUE 가 만든 백업 인덱스가 안 끼어 있는지 — 딱 일반 인덱스만
  • DATA_DEFAULT 가 있는 컬럼의 default 값에 개행·따옴표가 이상하게 안 남았는지

실패하면: SQL 조인 조건(src/oracle/describe.mjs 의 FK_SQL· INDEXES_SQL)부터 의심 — 특히 파티션 테이블·함수 기반 인덱스처럼 이 설계가 상정하지 않은 구조는 깨질 수 있다.

3
infer — LLM 결과 품질 확인
LLM 연결과 파서(환각 차단)가 실제로 잘 작동하는지.
export AKG_LLM_URL=http://llm.internal/v1 AKG_LLM_KEY=...
npx akg-collector infer --owner <스키마> --table <테이블>
  • purpose·컬럼 설명이 말이 되는 수준인지
  • dropped(환각)·missing(누락)이 너무 많지 않은지
  • 실 값(샘플 row)이 프롬프트로 안 나갔는지 — 기본 OFF 이므로 별도로 켜지 않았다면 당연히 안 나감
4
push dry-run — 최종 조립 결과 확인
아직 아무것도 만들지 않는다. akg 접속 정보까지 필요하지만(존재확인 GET), 여기서도 생성은 안 한다.
export AKG_BASE_URL=http://akg.internal AKG_EDITOR_TOKEN=...
npx akg-collector push --owner <스키마> --table <테이블>
  • would_create 로 나오는지(그 테이블에 akg 문서가 이미 있으면 skip — 그럼 다른 테이블로)
  • id 가 lower(owner.table) 규칙대로 나오는지
5
push 실제 1건 — 미리 골라둔 희생 테이블로
실제로 akg 에 문서 하나를 만들어보는, 이 체크리스트에서 유일하게 되돌리기 번거로운 단계. 그래서 시작 전에 골라둔 "중요하지 않은 작은 테이블"로만 한다.
npx akg-collector push --owner <스키마> --table <희생 테이블> --push
  • akg 대시보드에서 문서가 실제로 보이는지, tier 가 전부 inferred(또는 값 없는 슬롯은 scaffold)인지 — confirmed 는 절대 아니어야 한다
  • evidence 형식이 "catalog → comment → llm" 순서로 붙어 있는지
  • keywords 의 inject 가 pointer 인지
  • 같은 명령을 한 번 더 돌려서 skip (이미 있음) 이 나오는지 — 재개 정책이 실제로 작동하는지 확인하는 지점
6
거버넌스 재확인 — 코드가 아니라 사람이 결정
editor 토큰으로 직접 생성하는 방식은 akg 의 propose→adopt 사람 검토 경로를 건너뛴다 (README·docs/usage.html 에 이미 적어둔 caveat). "이미 있는 문서는 절대 안 건드린다"는 전제로 안전하다고 판단했지만, 이건 코드로 증명할 수 없는 조직·정책 판단이다.

확인할 것: 5단계에서 만든 문서가 akg 운영 관점에서 "사람 검토 없이 바로 라이브되는 게 괜찮다"는 정책과 맞는지. 안 맞으면 editor 직접생성을 agent 역할 + POST /api/proposals 큐로 바꾸는 재설계가 필요하다 — 부트스트랩 규모(수백 개)와는 상충하니 그 트레이드오프도 같이 검토.

7
본 가동 — 대상 리스트로 부트스트랩
1~6 이 다 통과했으면, 대상 테이블을 파일로 정리해서 실제 규모로.
npx akg-collector run --owner <스키마> --tables-file ./bootstrap.txt --push
  • 실행 로그에서 create/skip 비율이 기대와 맞는지
  • 중간에 끊겨도 그냥 같은 명령 다시 돌리면 된다(재개 = 스킵 정책)
