● Phase 0~4 구현 완료 — 실 Oracle/akg 라이브 미검증

akg-collector

Oracle 스키마를 읽어 agent-knowledge-governance(akg)의 db-schema 문서를 만드는 CLI 수집기. github.com/ollybaysion/akg-collector

무엇을 하는가

팩트는 DB 에서, 의미는 LLM 에서, 확정은 사람이. 만들어지는 문서 안에서 세 출처가 이렇게 나뉜다.

출처들어가는 자리티어
Oracle 카탈로그 (컬럼·타입·PK·FK·코멘트)body.catalog팩트 — 티어 없음
LLM 추론 (테이블 용도·컬럼 의미)purpose · columnDescsinferred
사람 확인같은 슬롯confirmed — akg 서버에서 승격

파이프라인

1
discover
스키마 안 대상 테이블 목록
2
describe
컬럼·타입·NULL·코멘트·PK·FK·인덱스
3
infer
LLM 추론 — 테이블 1개 = 호출 1회
4
compose
팩트 + 슬롯 + evidence 조립
5
push
GET 존재확인 → 없으면 POST

3(infer)이 테이블 단위인 이유: 컬럼 의미는 테이블 전체를 봐야 제대로 나온다 — SNSR_ID 가 무엇인지는 옆에 EQP_ID·MEAS_TIME 이 있는 걸 봐야 안다.

설치

# oracledb 는 6.x 기본이 thin 모드라 Oracle Instant Client 설치 없이 붙는다
npm install

커맨드

커맨드가 실제로 안 쓰는 접속 정보는 요구하지 않는다 — 필요한 만큼만 환경변수를 준비하면 된다.

discover --owner OWNER [--like PATTERN]

ORACLE_*

스키마 안의 테이블 목록을 나열한다.

export ORACLE_USER=... ORACLE_PASSWORD=... ORACLE_CONNECT_STRING=host:1521/service
npx akg-collector discover --owner FDC

describe --owner OWNER --table TABLE

ORACLE_*

테이블 하나의 구조(컬럼·PK·FK·인덱스·통계)를 JSON 으로 찍는다.

npx akg-collector describe --owner FDC --table FDC_SENSOR

infer --owner OWNER --table TABLE

ORACLE_*AKG_LLM_*

describe 결과로 LLM 추론만 돌려본다 — compose·push 는 하지 않는다.

export AKG_LLM_URL=http://llm.internal/v1
export AKG_LLM_KEY=...   # 사내 게이트웨이가 인증 안 걸면 생략
npx akg-collector infer --owner FDC --table FDC_SENSOR

push --owner OWNER --table TABLE [--push]

ORACLE_*AKG_LLM_*AKG_*

테이블 하나를 처음부터 끝까지 — describe→infer→compose→push. 기본은 dry-run.

export AKG_BASE_URL=http://akg.internal AKG_EDITOR_TOKEN=...
npx akg-collector push --owner FDC --table FDC_SENSOR           # dry-run, 뭘 만들지만 보여준다
npx akg-collector push --owner FDC --table FDC_SENSOR --push    # 실제로 생성

run --owner OWNER [--push]

ORACLE_*AKG_LLM_*AKG_*

여러 테이블을 한 번에. 대상은 세 가지 방식 중 하나로 고른다.

# A) 스키마 전체 (discover)
npx akg-collector run --owner FDC --push

# B) 직접 지정 (discover 생략)
npx akg-collector run --owner FDC --tables FDC_SENSOR,FDC_EQUIPMENT --push

# C) 파일로 지정 — 한 줄에 테이블 하나, # 은 주석. 수백 개짜리 부트스트랩용
npx akg-collector run --owner FDC --tables-file ./bootstrap.txt --push

dry-run 이 기본값인 이유

push·run 은 --push 를 명시하지 않으면 아무것도 만들지 않는다 — "이런 문서를 이런 id 로 만들 거야" 만 콘솔에 찍는다. 실수로 스키마 전체를 라이브에 쏟아붓는 사고를 막기 위한 기본값이다. 

$ npx akg-collector run --owner FDC
(dry-run) fdc.fdc_sensor    → 생성될 예정
(dry-run) fdc.fdc_equipment → 스킵 (이미 있음)
...
12개 생성될 예정, 3개 스킵. 실제로 하려면 --push.

재개(resume)

별도의 체크포인트 파일이 없다. 스킵 정책 자체가 재개다 — akg 에 이미 문서가 있는 테이블은 describe·infer 를 하기도 전에 걸러진다. 그래서 중단된 파이프라인을 처음부터 다시 돌려도, 이미 push 된 테이블에는 LLM 호출조차 다시 나가지 않고 결과는 똑같다.

알아둘 것

사람 검토 없이 문서가 바로 라이브된다.

akg 의 role 랭크는 viewer < editor < approver 이고 agent 는 그 사다리 밖 별도 역할이다. 존재확인(GET)·생성(POST) 둘 다 커버하려면 editor 토큰이 필요한데, 그건 akg 의 propose→adopt 사람 검토 경로를 건너뛴다는 뜻이다. "이미 있는 문서는 절대 건드리지 않는다(병합 없음)"는 전제 때문에 안전하다고 판단해 이 경로를 택했지만, 사내 반입 전에는 재확인이 필요하다.

실 Oracle/akg 인스턴스로 검증된 적이 없다.

테스트 74개는 전부 fixture 와 주입된 가짜 클라이언트로 돈다 — describe 의 SQL 매핑은 "SQL 이 돌려준다고 가정한 행"을 기존 fixture 와 바이트 단위로 대조한 것뿐, SQL 문법·조인 정확성 자체는 실 스키마에서 처음 확인해야 한다. oracledb 접속은 가짜 주소로 끝까지 태워 배선은 맞다는 걸 확인했다(thin 모드라 Instant Client 불필요).
